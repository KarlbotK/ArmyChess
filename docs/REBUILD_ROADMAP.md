# ArmyChess 分步改造路线

原则：先保护原玩法，再替换危险基础设施，最后建设新前端。每一阶段都有可验证的完成门槛，避免一次性重写后无法判断规则是否走样。

## 当前进度（2026-09-20）

- 阶段 0：已完成；
- 阶段 1：核心规则模块、工程构建与首批规则/隐私测试已完成，完整分支覆盖继续补齐；
- 阶段 2：房间、会话恢复、布局、行棋、聊天、投降、幂等、输入限制、服务端回合超时与再战已完成；生产级限流待完成；
- 阶段 3–4：大厅、等待区、可编辑布阵、完整规则说明、倒计时、结算再战和核心对局前端已完成；拖拽布阵与阵型预设待完成；
- 阶段 5：已完成本地四浏览器联机、结算再战、超时换手与 1280×720 设计验收；兼容性、压力、读屏和预发布验收待完成；
- 阶段 6：已提供容器化入口，尚未绑定生产域名或执行公网发布。

## 阶段 0：保存基线与确认产品范围

产出：

- 旧版审计、产品需求文档和本路线图；
- 旧版棋盘截图与可复现的四人启动故障；
- 明确保留的规则与需要重写的边界；
- 三套视觉方向，选定其中一套作为实现目标。

完成门槛：视觉方向被选定；MVP 核心旅程不再有范围歧义。

## 阶段 1：规则引擎与工程基线

产出：

- 建立标准构建、测试、格式化、静态检查和 CI；
- 将棋盘、布局、移动、战斗、回合与胜负提取为无网络依赖的领域模块；
- 为现有规则建立特征测试，修复四人启动竞态、越界、非法布局和全局退出；
- 移除仓库中的编译产物，补齐 README、许可证选择说明和忽略规则。

完成门槛：规则测试覆盖所有棋子和特殊地形；同一测试在本地和 CI 可重复通过。

## 阶段 2：安全的实时服务

产出：

- Spring Boot WebSocket 服务与版本化 JSON 协议；
- 创建/加入房间、座位、准备、布阵、行棋、聊天、投降、结算、再战；
- 会话恢复、90 秒断线保留、心跳和幂等动作；
- 房间隔离、服务端计时、输入校验、限流、结构化日志和健康检查。

完成门槛：四个脚本客户端可稳定完成整局；非法请求不会改变棋局或中止房间。

## 阶段 3：Web 前端骨架

产出：

- React + TypeScript + Vite 工程；
- 设计令牌、字体、颜色、间距、动效和响应式断点；
- 首页、房间等待区、规则页、设置页；
- WebSocket 状态层、错误恢复、加载/空状态和基础无障碍。

完成门槛：用户可在浏览器创建房间、邀请并看到四人准备状态；刷新可恢复座位。

## 阶段 4：核心对局前端

产出：

- 可缩放四国棋盘、四方视角、棋子语义层和合法路径提示；
- 布阵交换、拖拽、随机、重置、预设与实时校验；
- 回合、倒计时、战斗时间线、聊天、投降和结算再战；
- 键盘操作、高对比模式、色觉辅助、减少动态效果。

完成门槛：四位真人通过浏览器完成“进房—布阵—对局—结算—再战”全流程。

## 阶段 5：产品化与质量

产出：

- 端到端自动化、多人并发、断线与恶意请求测试；
- 兼容性、性能和可访问性验收；
- 埋点、监控、告警、隐私说明和故障恢复手册；
- 预发布环境的邀请制试用。

完成门槛：发布门槛全部满足，阻断级问题为零。

## 阶段 6：上线与迭代

产出：

- 生产域名、HTTPS/WSS、容器部署和回滚；
- 小流量上线与运行指标观察；
- 根据真实数据决定机器人、战绩、观战和回放的优先级。

完成门槛：核心成功率和稳定性达到 PRD 目标，项目具备持续发布能力。

## 实施顺序说明

前端不会直接连接旧 `ObjectInputStream` 服务。阶段 1 和 2 先建立可验证、可公开暴露的协议与服务端事实源；阶段 3 和 4 再实现用户可见界面。这样既保留旧项目最有价值的规则，也避免把新界面绑在无法上线的网络层上。
